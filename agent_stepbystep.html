Step 2 · The Boss Agent
Create the Orchestrator Agent
The Orchestrator is the PM of your AI team. It reads your one-sentence prompt, builds a plan, and dispatches worker agents. It's like a conductor — except it never takes a bow and works 24/7 for free.
2.1
Define the Orchestrator in copilot-agents.yml
Open .github/copilot-agents.yml — this is the master config file for ALL agents
›

Open .github/copilot-agents.yml in VS Code and define the Orchestrator block. This tells Copilot who is in charge and what triggers the whole pipeline.

# ═══════════════════════════════════════════════════ # GitHub Copilot Multi-Agent Configuration # E-Commerce SDLC Automation # ═══════════════════════════════════════════════════ version: "1.0" project: "ecommerce-app" description: "AI-powered SDLC for Angular + .NET + Postgres" # ── ORCHESTRATOR (The Boss) ────────────────────────── orchestrator: name: "pm-agent" display_name: "PM Orchestrator" model: "gpt-4o" persona: | You are a senior project manager and system orchestrator. Parse requirements into structured tasks. Assign tasks to the right agents. Track completion. Report status clearly. Never do work meant for other agents. triggers: - on_copilot_chat_prompt # triggered from Copilot Chat - on_issue_created # triggered when a GH Issue is filed - on_manual_dispatch # triggered by the "one click" button inputs: - type: natural_language_prompt description: "Describe what to build" outputs: - docs/requirements.md - docs/task-graph.json
2.2
Create the Orchestrator's system prompt file
The persona block tells the Orchestrator HOW to think and behave
›

Create .github/agents/orchestrator.prompt.md — this is the detailed instruction set for the Orchestrator. Think of it as an extremely detailed job description that the agent actually reads (unlike most employees).

markdown · .github/agents/orchestrator.prompt.mdCreate This
# Orchestrator Agent — System Instructions ## Your Role You are the PM Orchestrator. You receive a natural language prompt describing a feature or project. Your job is to: ## Step-by-Step Process 1. Parse the user prompt into structured requirements 2. Create user stories in format: "As a [user], I want [action]" 3. Break stories into technical tasks per layer (FE, BE, DB) 4. Build a task dependency graph (JSON format) 5. Write requirements to docs/requirements.md 6. Write task graph to docs/task-graph.json 7. Emit AGENT_START signal with the task-graph as context ## Agent Routing Rules - Architecture tasks → architecture-agent - Angular/UI tasks → frontend-agent - .NET API tasks → backend-agent - Database tasks → database-agent - Test tasks → qa-agent - Security review → security-agent - Docker/CI tasks → devops-agent - Docs tasks → doc-agent ## Context Object Structure (emit this to all agents) Provide a shared context JSON containing: - project_name, description, stack - user_stories[], technical_tasks[] - api_contract_path, db_schema_path - agent_assignments{}
💡
Why a separate .md file? It keeps your YAML clean and lets you version-control agent instructions separately. When the Orchestrator starts making weird decisions, you edit this file — not the entire config. Debugging AI is already hard enough.
The Orchestrator reads this file every time it runs. It's the only employee who actually reads the employee handbook.

Step 3 · System Design
Create the Architecture Agent
This agent reads the requirements and decides HOW the system is built — what talks to what, where data lives, and what the API looks like. It's the person who draws boxes and arrows on whiteboards, except it actually finishes in time.
3.1

3.2
Create architecture.prompt.md — The agent's brain
Tell the agent how to design the system and what to produce
›
markdown · .github/agents/architecture.prompt.mdCreate This
# Architecture Agent — System Instructions ## Stack (NEVER deviate from this) - Frontend : Angular 17 with standalone components - Backend : .NET Core 8 WebAPI, Clean Architecture - Database : PostgreSQL 16 - Auth : JWT Bearer tokens ## Your Tasks (in order) 1. Read docs/requirements.md 2. Design the system architecture 3. Define all API endpoints based on user stories 4. Generate openapi.yaml (OpenAPI 3.0 spec) - Every endpoint must have: path, method, request body, response - This file is LAW for frontend and backend agents 5. Design PostgreSQL schema (all tables, columns, FKs, indexes) 6. Write ARCHITECTURE.md with: component diagram, tech decisions ## API Endpoints Required for E-Commerce - GET/POST/PUT/DELETE /api/products - GET /api/products/{id} - GET/POST /api/cart - POST /api/cart/items, DELETE /api/cart/items/{id} - POST /api/orders, GET /api/orders, GET /api/orders/{id} - POST /api/auth/login, POST /api/auth/register ## Output Quality Rules - openapi.yaml must be valid and parseable - Every DTO must match OpenAPI schema exactly - Never invent endpoints that weren't in requirements
⚠️
openapi.yaml is sacred! Every agent downstream will read this file. If the Architecture Agent produces garbage here, the Frontend and Backend agents will build garbage on top of garbage. Garbage lasagna. Not what we want.
The Architecture Agent is the only one who gets to make design decisions. All other agents must respect them. It's like a constitution — if you don't like it, you file a PR.

# Database Agent — PostgreSQL DBA Instructions ## Tables to Create - users (id, email, password_hash, full_name, created_at) - categories (id, name, slug, description) - products (id, name, description, price, stock_qty, category_id FK, image_url, created_at) - carts (id, user_id FK, created_at, updated_at) - cart_items (id, cart_id FK, product_id FK, quantity, unit_price) - orders (id, user_id FK, status, total_amount, shipping_address JSONB, created_at) - order_items (id, order_id FK, product_id FK, quantity, unit_price) ## Schema Rules - Use UUID for all primary keys (gen_random_uuid()) - All timestamps in UTC with DEFAULT NOW() - All money columns as NUMERIC(10,2) — never FLOAT - Add CHECK constraints (price > 0, quantity >= 0) - snake_case for all table and column names ## Indexes to Create - idx_products_category_id - idx_products_price (for sorting/filtering) - idx_cart_items_cart_id - idx_orders_user_id - idx_orders_status - Unique index on users.email ## Seed Data - 3 categories (Electronics, Clothing, Books) - 30 products across categories (realistic names + prices) - 2 test users (customer, admin) ## EF Core Migrations - Generate InitialCreate migration matching the SQL schema - Ensure column types map correctly to .NET types
Database Agent uses NUMERIC(10,2) for prices. It has seen things. It has seen FLOAT used for currency. It will not speak of what it witnessed.

Step 7 · Quality
Create the QA Agent
The QA Agent writes tests, runs them, finds failures, tells the responsible agents to fix them, and re-runs. It loops until green. It has no concept of "good enough." You'll love it and fear it simultaneously. That's normal.
7.1
Add QA Agent to copilot-agents.yml
QA depends on both frontend and backend being complete
›
yaml · Append to agents: listAppend This
# ── AGENT 5: QA ─────────────────────────────────── - name: "qa-agent" display_name: "QA Engineer" model: "gpt-4o" prompt_file: ".github/agents/qa.prompt.md" depends_on: - "frontend-agent" - "backend-agent" tools: - read_files - write_files - run_terminal - run_tests loop_on_failure: true # retries until all tests pass ♻️ max_retries: 3 failure_escalation: # who to ping if still failing - "backend-agent" - "frontend-agent" coverage_threshold: 80 # fail if coverage drops below 80% outputs: - "tests/**" - "coverage-report.xml" emit_signal: "QA_DONE"
🔁
loop_on_failure: true is the magic. If tests fail, the QA Agent tells the relevant agent to fix the issue, then re-runs. It doesn't give up. It doesn't file a bug ticket for "someone else to handle." It finishes what it started.

# QA Agent — Test Engineer Instructions ## Test Layers to Create Layer 1: Unit Tests (.NET — xUnit) - ProductServiceTests → test all service methods - OrderServiceTests → test order creation, status changes - CartServiceTests → test add/remove/clear - AuthServiceTests → test login, register, token gen - Run with: dotnet test --collect:"XPlat Code Coverage" Layer 2: Unit Tests (Angular — Jest) - ProductService: mock HTTP calls, test CRUD methods - CartStore: test signal state transitions - AuthService: test login/logout/token storage - Run with: ng test --watch=false --code-coverage Layer 3: Integration Tests (.NET) - Use WebApplicationFactory for real HTTP calls - Use Testcontainers for real Postgres DB - Test complete request→response cycles for each endpoint Layer 4: E2E Tests (Playwright) - Product browsing flow: visit /products, see grid, click product - Cart flow: add product, view cart, update quantity - Checkout flow: fill form, submit order, see confirmation - Auth flow: register, login, access protected pages ## After Writing Tests 1. Step 8 · Security
Create the Security Agent
The Security Agent is paranoid by design. It runs after QA and scans everything — OWASP Top 10, hardcoded secrets, dependency vulnerabilities, JWT misconfigurations. If it finds something bad, the pipeline stops. Full stop. No "we'll fix it later." Later never comes.

markdown · .github/agents/security.prompt.mdCreate This
# Security Agent — Paranoid Professional Instructions ## Scan Commands to Run - Semgrep: semgrep --config=auto backend/ frontend/ - npm audit: npm audit --audit-level=high (in frontend/) - dotnet: dotnet list package --vulnerable --include-transitive - Secret scan: grep -r "password\|secret\|apikey\|connstring" --include="*.cs" --include="*.ts" ## OWASP Top 10 Checks A01 Broken Access Control → verify [Authorize] on all user endpoints A02 Cryptographic Failures → JWT secret must be 256-bit min, HTTPS only in prod A03 Injection → verify all DB calls use parameterized queries (EF Core = ✅) A05 Security Misconfiguration→ CORS not set to wildcard (*) in prod A07 Auth Failures → password hashing uses BCrypt (not MD5/SHA1) A09 Logging Issues → no passwords or tokens logged anywhere ## Auto-Fix Rules - If HTTPS not enforced in prod → add UseHttpsRedirection() to Program.cs - If CORS is wildcard → restrict to specific origins - If JWT expiry > 24h → reduce to 1h access token - If password plain text → replace with BCrypt hash ## Hard Blockers (pipeline stops) - Hardcoded credentials in any file - SQL injection via raw string concatenation - JWT secret less than 32 characters - Any critical CVE in dependencies ## Outputs - Write SECURITY.md with findings summary - Write security-report.json with machine-readable results
Security Agent once found a JWT secret of "secret123". It didn't say anything. It just replaced it silently and went home early. We don't talk about that day.

Step 11 · The Glue
Wire All Agents Together — The Context Bus
This is where agents stop being isolated scripts and become a team. The Context Bus is a shared JSON object that every agent reads from and writes to. It's the group chat. The shared brain. The thing that prevents agents from building the same component twice.

Bonus · Pro Tips
Things Nobody Tells You (Until It's Too Late)
Hard-won wisdom from the agent-whispering trenches
💡
Prompt Quality = Output Quality (No Surprises There)
Your one-sentence prompt is the seed of everything. Make it count.
›
❌
Bad prompt: "Build an e-commerce app" — Agents will make 47 decisions you didn't ask for. Some of them will be wrong. You'll have opinions about it later.
✅
Good prompt: "Build an e-commerce app with: product listing with search and filter, shopping cart with quantity management, Stripe checkout, and order history. Users log in via email. Admin can add/edit products." — Now the agents have context. Now they can shine.
The more specific your prompt, the less specific your regrets.
🔍
Review the openapi.yaml Before Letting Other Agents Run
This one file is the source of truth for ALL agents — get it right first
›
  • 👀 After the Architecture Agent finishes, STOP and review openapi.yaml before proceeding
  • 👀 Check: are all endpoints correct? Are response shapes right? Are required fields marked?
  • 👀 If something is wrong, tell the Architecture Agent to fix it via chat BEFORE frontend/backend run
  • 👀 Once frontend and backend are built from a wrong spec, fixing it means rebuilding both. Pain.
Reviewing openapi.yaml before the build is like checking the blueprint before constructing a skyscraper. Obvious in retrospect. Never done in practice. Do it.
🛠️
Use Incremental Runs for Complex Features
Don't try to build everything in one shot for large projects
›

For a real production app, break it into runs:

  • 🏃 Run 1: Core auth + products listing (foundation)
  • 🏃 Run 2: Shopping cart + checkout (commerce core)
  • 🏃 Run 3: Order management + admin panel (management)
  • 🏃 Run 4: Email notifications + payment webhooks (advanced)
💡
Each run creates a PR. You review. You merge. You run the next. This gives you control checkpoints without slowing down the agents. Best of both worlds.
