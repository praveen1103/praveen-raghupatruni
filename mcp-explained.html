01 — The Problem

AI Is Smart But Blind

Picture the smartest person you know. Now lock them in a room with no phone, no internet, no windows — just a notepad with everything they knew up until a year ago. That's your LLM without tool integrations.

Your AI knows Shakespeare and Kubernetes — but it can't check your Jira tickets, read your database, or tell you what the weather is right now. It's basically a galaxy-brained amnesiac.

Real Talk
Before MCP, connecting an LLM to a tool meant writing a custom integration every. single. time. GitHub? Custom code. Slack? More custom code. Your internal database? Oh buddy, strap in.

Every team was reinventing the wheel. But not just any wheel — a square wheel. With splinters. The result was a N×M integration nightmare: N AI models × M tools = absolute chaos.

02 — What Is It?

MCP: The USB-C Port for AI

Model Context Protocol (MCP) is an open standard introduced by Anthropic in late 2024. It defines a universal interface between AI models (LLMs) and external tools, data sources, and services.

Think of it like this:

🔌

USB-C

One port. Works with your charger, monitor, headphones, and hard drive. MCP is USB-C for AI.

🍔

Restaurant Menu

The AI is the customer. The menu is MCP. The kitchen is your tools. You don't rewire the kitchen for each customer.

🧩

LEGO Interface

Any LEGO brick fits any other. MCP standardizes the studs so every tool snaps into every model.

Official Definition
MCP is a client-server protocol that lets AI models discover and call tools, read resources, and receive contextual information from external servers — in a standardized, model-agnostic way.

The magic word is model-agnostic. Build one MCP server for your GitHub integration, and every AI that speaks MCP can use it — Claude, GPT, Gemini, your neighbour's fine-tuned Llama model, whatever.

03 — Why We Need It

Because Nobody Wants to Be a Human API Wrapper

Without MCP, the workflow looks like this: user asks AI a question → AI gives a (possibly hallucinated) answer → user manually checks 6 different tools → user copy-pastes context back into the AI → repeat until either the answer is correct or someone quits their job.

Hot Take
Before MCP, you were basically the world's most overqualified copy-paste machine. A $200K human glue layer between an AI and a database.

MCP solves four real problems:

🔄

No More N×M

Instead of N models × M tools integrations, you write one MCP server per tool. Done.

🧠

Live Context

AI gets real-time data — your actual DB, your real files, your live Slack messages. No stale knowledge cutoffs.

🛡️

Controlled Access

MCP servers decide what the AI can see and do. Your AI can query a DB without getting root access to your server.

🚀

Composability

Combine MCP servers like building blocks. GitHub + Jira + Slack + your internal tools. One AI, full stack awareness.

The bottom line: MCP turns your AI from a "very smart chatbot that needs to be spoon-fed everything" into an "autonomous agent that actually knows what's going on in your codebase at 3am."

Real World Impact
Major tools already have official MCP servers: GitHub, Slack, Google Drive, Postgres, Brave Search, Puppeteer, and more. The ecosystem is growing fast.
04 — How It Works

The Protocol in Plain English

MCP is a client-server architecture built on top of JSON-RPC 2.0 over stdio or HTTP+SSE transport. But forget that for a second — here's the vibe:

🤖 AI Model (Client)
⟷
MCP Protocol
⟷
MCP Server
⟷
Your Tools / Data

An MCP server exposes three types of things:

Primitive What it is Example
Tools Functions the AI can call (with side effects) create_issue(), send_message(), run_query()
Resources Data the AI can read (no side effects) file://readme.md, db://users/schema
Prompts Pre-written prompt templates "Summarize this PR", "Review this SQL"

The AI connects to one or more MCP servers at startup. It then uses them during a conversation — calling tools, reading resources, using prompts — like a developer using an SDK.

json — MCP Tool Call 
// AI asks MCP server: "what tools do you have?"
{
  "jsonrpc": "2.0",
  "method":  "tools/list",
  "id":      1
}

// MCP server responds with available tools
{
  "result": {
    "tools": [{
      "name":        "create_github_issue",
      "description": "Creates a new issue in a GitHub repo",
      "inputSchema": {
        "type":       "object",
        "properties": {
          "title": { "type": "string" },
          "body":  { "type": "string" }
        }
      }
    }]
  }
}

// AI then calls the tool when needed
{
  "method": "tools/call",
  "params": {
    "name":      "create_github_issue",
    "arguments": {
      "title": "Bug: users can't log in after 3am",
      "body":  "Reproduced on prod. It's always 3am."
    }
  }
}
05 — Architecture

How the Pieces Fit Together

A typical MCP setup has three layers:

🖥️

MCP Host

The app running the AI — Claude Desktop, VS Code, your custom chatbot. It manages connections to MCP servers.

🔗

MCP Client

Embedded in the host. Maintains a 1:1 connection per server, handles the JSON-RPC communication.

⚙️

MCP Server

Lightweight process exposing your tool. It wraps the GitHub API, your DB, your filesystem — whatever you need.

Transport Options
stdio: Server runs as a child process. Good for local tools.
HTTP + SSE: Server runs remotely. Good for shared/cloud tools.
Both speak the same protocol — the host doesn't care which.

The beauty: your MCP server doesn't know or care which AI is calling it. Your AI doesn't know or care how the server is implemented. They just speak MCP and everyone's happy. That's the Unix philosophy applied to AI tooling.

typescript — minimal MCP server 
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({
  name:    "my-tool-server",
  version: "1.0.0"
});

// Expose a tool — AI can call this
server.tool(
  "get_weather",
  "Get current weather for a city",
  { city: z.string().describe("City name") },
  async ({ city }) => ({
    content: [{
      type: "text",
      text: await fetchWeather(city)  // your actual logic
    }]
  })
);

// Start listening
const transport = new StdioServerTransport();
await server.connect(transport);
